# 規約上クリーンな LINE 取得は Bot 参加が条件

**結論から言うと、「毎時チェックして Telegram に通知する」部分は Hermes と Mac mini で問題なく実現できるが、難所は LINE 側の取得で、個人アカウントで参加している通常グループを、規約上クリーンかつ他メンバーに見えない形で自動取得する公式手段は見つからなかった。** 公式に許されるのは「LINE 公式アカウント（Messaging API の Bot）をグループに招待し、webhook で受信する」方式だけで、Bot はメンバーとして見え、参加前の履歴は取れない。Hermes 同梱の LINE プラグインもこの方式の実装であり、取得能力は公式 Bot と同じである。Bot を入れたくない場合、現実的な選択肢は「手動エクスポート＋自動処理」（クリーン、ただし自動化は半手動）か、「beeper/line などの非公式ブリッジ」「通知ミラー」「画面読み取り」（いずれもグレーで、実運用の事例は見つからなかった）に限られる。三つのルールは、受信データを JSONL に溜めてコードで機械判定し、ローカル LLM には「共有すべきか」の一点だけを判断させる設計で実装できる。ただし「グループに人物A がいない」判定は、未認証の公式アカウントでは「発言した人」しか把握できず、確実性が下がる。以下の推奨は調査結果からの推論であり、実機検証までは仮説として扱う。

出典の確度は次の記号で示す。[公式] LINE/Hermes の公式ドキュメント、[ソース] リポジトリのソース、[3rd] サードパーティ記事・リポジトリ、[推論] 調査結果からの筆者推論。公式ドキュメントは要約取得ツール経由で読んでおり、表現が言い換えられている可能性がある。LINE 公式ヘルプ（help.line.me）の本文は取得できなかった。Hermes の cron/Telegram/ローカル LLM 運用の背景は別レポートに譲り、ここでは LINE 固有の論点に絞る。

## 結論：各要件の可否と、クリーンな手段・グレーな手段の線引き

全体を一言でまとめると、**「Bot をグループに入れてよいなら、全要件が条件付きで実現可能。入れられないなら、規約上クリーンな完全自動化は見つからなかった」**となる。要件ごとの結論は次のとおり。

| 要件 | 判定 | 根拠と条件 |
|---|---|---|
| 毎時の自動取得 | 条件付き | 公式 Bot なら webhook で常時受信して蓄積し、毎時はその蓄積を読む方式。LINE には履歴取得 API が無く（「Webhook を受信した後で、あらためてテキストを取得するための API はありません」）、Bot 参加前・停止中の発言は取れない可能性が高い ([公式](https://developers.line.biz/ja/docs/messaging-api/receiving-messages/))。公式の手動エクスポートは人手操作が前提 |
| 今日の会話だけ | できる | イベントに `timestamp`（ミリ秒）と `groupId`/`userId` が含まれるので JST 変換で機械判定できる ([公式](https://developers.line.biz/ja/docs/messaging-api/receiving-messages/)、[公式](https://developers.line.biz/ja/docs/messaging-api/group-chats/)) |
| グループに人物A がいない | 条件付き（弱い） | メンバー ID 一覧 API は認証済み（またはプレミアム）アカウント限定 ([公式](https://developers.line.biz/en/docs/messaging-api/getting-user-ids/))。未認証だと発言者の userId しか集められない。しかも userId は Bot ごとに異なる ID で、人物A 本人の ID を紐付ける運用が要る [推論] |
| 公式アカウントでない | できる（Bot 方式では自明） | Messaging API の Bot が見るのはグループと Bot 宛 1:1 の会話だけで、ユーザー本人の個人アカウントが持つ公式アカウントとのトークは存在自体が見えない [推論]。個人アカウント側の取得（ブリッジ等）では、トーク種別を判別できるかは未確認 |
| Telegram 通知 | できる | Hermes は接続済みで、cron の `deliver: telegram` が使える ([公式](https://hermes-agent.nousresearch.com/docs/user-guide/features/cron)) |
| ローカル LLM で判断 | できる（精度は要検証） | 判断対象を事前整形して渡せば、ツール呼び出し不要の分類タスクにできる。小型モデルの精度・出力形式遵守は事例が見つからず未確認 [推論] |

規約上の線引きは次のとおり。**クリーン**なのは、公式 Messaging API の Bot と、ユーザー自身が手で行うトーク履歴の保存・送信である。**グレー**なのは、個人アカウントのセッションで動く非公式ブリッジ、通知の転用、画面の自動操作で、LINE 利用規約は「BOT、チートツールその他の技術的手段を利用して当社サービスを不正に操作する行為」(15(5))、不当な態様のリバースエンジニアリング (15(6))、第三者の個人情報の不正な収集・蓄積 (15(8)) を禁じている ([公式規約](https://terms.line.me/line_terms/?lang=ja))。非公式クライアントを名指しした条項は確認できなかったが、読み取り専用の個人利用がこれらに当たるかは規約文言から断定できない [推論]。アカウント制限リスクは「ゼロではなく、実態が不透明」と見るのが妥当である。

## 推奨：Hermes は判断、取得と判定はコードに分ける

Hermes の公式機能（cron の `script`、`wakeAgent:false`、`[SILENT]`）は、「決定的な前処理でゲートし、LLM は最小限の判断に絞る」設計とよく噛み合う ([公式](https://hermes-agent.nousresearch.com/docs/user-guide/features/cron))。この思想を LINE に適用して、リスクの低い順に四段階で進める案を示す。以下はすべて推論であり、実機での検証を前提とする。

### 設計の原則

ルール三つのうち機械的に判定できるものは、すべてコード（Python 等）で処理する。具体的には「今日（JST）」「グループに人物A の userId が現れていない」「トーク種別がグループ」の三つで、LLM に渡す前に候補を絞る。LLM に任せるのは、絞り込まれたメッセージ群について「人物A に共有すべき可能性があるか」の判断だけで、出力は固定フォーマット（JSON 等）に限定する。ローカル小型モデルが `[SILENT]` を正確に返す保証は調べた範囲では確認できなかったため、判断結果を外部スクリプトが解析して Telegram に送る構成のほうが安定する可能性がある ([公式](https://hermes-agent.nousresearch.com/docs/user-guide/features/cron)、確度は推論）。

### 段階 0：手動エクスポートでローカル LLM の判断品質を確かめる（リスク最小）

最小構成は、PC 版 LINE の「トークを保存」（.txt、写真・動画・スタンプは含まれない ([3rd](https://minto.tech/line-chat-history-export-pc/))）で対象トークを保存し、ホストの監視フォルダに置いて、スクリプトが今日の分を抽出し、ローカル LLM が判断して Telegram に通知する流れである。**この段階の目的は、自動取得ではなく「判断の質と通知のうるささ」の検証**にある。規約リスクはほぼ無く、Bot も要らない。欠点は人手が要ること、メンバー一覧が含まれないため「人物A がいない」判定を事前の手作業（対象グループを人が選ぶ）に頼ることである。

```
[人: PC版で「トークを保存」] -> ~/line_export/*.txt
   -> [launchd 毎時: parse.py（今日JSTだけ抽出・既通知IDを除外）]
   -> [Hermes cron / hermes chat -Q（ローカルLLM: 共有すべきか JSON で判定）]
   -> [post.py: 結果をパースして Telegram Bot API へ]
```

### 段階 1：公式 Bot を検証用グループ 1 つで試す

後藤さんが Bot の参加に同意でき、テスト用グループを用意できる場合は、公式 Bot を自前の受信スクリプトとして立てる。Messaging API の webhook は公開 HTTPS を要し、`x-line-signature` の検証が必須である ([公式](https://developers.line.biz/ja/docs/messaging-api/receiving-messages/))。Mac mini では固定の名前付き Cloudflare Tunnel を使い、公開するパスを webhook 用に限定する（Hermes のドキュメントも固定トンネルを推奨 ([公式](https://hermes-agent.nousresearch.com/docs/user-guide/messaging/line))。パス限定は推論）。受信スクリプトは署名を検証し、`webhookEventId` で重複を除いて JSONL に追記するだけの薄い構成にする。Hermes の LINE プラグインは使わない。理由は前節で述べた応答リスクで、受信と判断を分けるほうが安全だからである。

```
LINE グループ --(Bot が参加)--> LINE Platform
   --> HTTPS Tunnel --> receiver.py（署名検証・webhookEventId で重複除去）
   --> /data/line/messages.jsonl（id, ts, groupId, userId, type, text）
```

### 段階 2：毎時の cron と判定・重複防止を載せる

蓄積した JSONL に対して、Hermes の cron を毎時（`0 * * * *` または `every 1h`）で回す。ジョブは「前処理スクリプト → LLM 判断 → Telegram 配信」の三段にする。前処理は次の順で、決定的に処理する。

```
messages.jsonl
  -> pre.py: 今日(JST) の発言のみ
          -> 対象グループのみ（許可リスト）
          -> userId 集合に人物A を含むグループは除外
          -> notified.json にある ID を除外
          -> 残りが 0 件なら {"wakeAgent": false} を出力して終了（LLM を呼ばない）
  -> Hermes（ローカルLLM、toolsets 最小）: 共有すべきなら要約、なければ [SILENT]
  -> deliver: telegram
  -> 配信成功後に notified.json へ ID を追記
```

Hermes cron の要点は、調査で確認できた範囲で次のとおり。スケジュールは `every 1h`/cron 式、ジョブに `script`（`$HERMES_HOME/scripts/` 配下）、`enabled_toolsets`、`deliver`、`model`/`provider` を指定でき、`deliver` には `telegram`（ホームチャンネル）や `telegram:<chat_id>` が使える。最終応答に `[SILENT]` が含まれると配信が抑止され、スクリプトの最終行に `{"wakeAgent": false}` を出せば当該 tick の LLM 呼び出しがスキップされる ([公式](https://hermes-agent.nousresearch.com/docs/user-guide/features/cron))。`hermes cron create` の位置引数はドキュメントで確認できなかったため、`--help` で確かめる必要がある。**重複通知防止は、Hermes の `continuity` や記憶には頼らず、自前の状態ファイルで行う**。ドキュメント自身が、内部の `state.db` を読まず自前の状態ファイルで制御することを勧めている ([公式](https://hermes-agent.nousresearch.com/docs/user-guide/features/cron))。

### 段階 3：Bot を入れられない場合の発展案（グレー、自己責任）

Bot を入れられない場合の次善策は、beeper/line を用いた Matrix ブリッジである。2026 年も保守され、グループに対応し、MIT ライセンスで、matrix.org では「Stable / Recommended」と掲載されている ([3rd](https://github.com/beeper/line)、[3rd](https://matrix.org/ecosystem/bridges/line/))。ただし LINE の Chrome 拡張クライアントとして動作するため、LINE 側の変更で壊れ得る点、規約上グレーである点、日本語コミュニティの事例が見つからない点は変わらない。**導入するなら、まず捨てても困らないサブアカウントで検証し、本アカウントへの適用は規約リスクを理解したうえでの判断とする**のが妥当である。セットアップ手順は本レポートの対象外とする。通知ミラーや画面読み取りは、取りこぼしと脆さのため推奨しない。

## 安全面：プロンプトインジェクション、他メンバーの発言、公開口

グループの発言は攻撃者が制御し得る入力であり、Hermes のエージェントはターミナルを含む広いツールを持つ ([公式](https://hermes-agent.nousresearch.com/docs/user-guide/features/api-server))。Webhook のドキュメントも、署名は送信元を保証するだけでペイロードの安全性は保証しないと警告している ([公式](https://hermes-agent.nousresearch.com/docs/user-guide/messaging/webhooks))。対策として、判断ジョブの `enabled_toolsets` を最小（理想は無し）にし、メッセージ本文は「データ」であると明示した区切りで渡し、出力を固定 JSON に限り、スクリプトが型と長さを検証してから通知する [推論]。また、LINE 側の webhook を受ける口は、署名検証を行う受信スクリプトだけを公開し、Hermes の API サーバー (8642) や webhook (8644) は公開しない。

倫理・法的な注意として、他メンバーの発言を蓄積して処理することには、規約 15(8) の「第三者に関する個人情報等を不正に収集・蓄積」の観点と、メンバーの期待（Bot が入っていると知らされるか）の問題がある ([公式規約](https://terms.line.me/line_terms/?lang=ja))。個人情報保護法は一般に事業として個人情報データベースを扱う者を対象とし、私的利用は対象外と考えられるが、条文とガイドラインは直接確認できておらず、**法的な断定はできない** [推論]。ローカル LLM に限定すれば外部事業者への第三者提供は避けられ、リスクは小さくなる [推論]。Bot 方式では、メンバーへの周知（Bot を入れる理由の説明）と、保存期間の限定（今日分のみ保持、翌日に削除）、メッセージが取り消された場合の削除（公式が勧めている ([公式](https://developers.line.biz/ja/docs/messaging-api/receiving-messages/))）を運用に組み込むことを推奨する。

## 未確認事項、実機検証、後藤さんへの質問

調査で確認できていない点が多いため、決定前に次の小さな検証を行うのがよい。

| 未確認事項 | 検証手順（小さく） |
|---|---|
| グループでメンション無しの全発言が届くか | テスト用グループに Bot を入れ、受信スクリプトで生イベントを記録する（応答は返さない） |
| 取り消し・編集イベントの扱い | テスト発言を取り消し、`unsend` イベントを確認して JSONL から削除できるか見る |
| 未認証アカウントで人物A の在否が判るか | メンバー ID API を叩いて拒否されるか確認。拒否なら発言者ベースの判定に切り替える |
| 人物A の userId の紐付け | 人物A が Bot と友だちになるか、そのグループで 1 度発言したときの userId を記録できるか |
| 手動エクスポート txt の形式（日時・名前・システムメッセージ） | 実際に保存して 1 日分を確認 |
| ローカル LLM の判断精度と出力形式遵守 | 手動エクスポートの 1 日分で、共有すべき/不要の正解を人が付けて比較 |
| Hermes cron の `script` 出力が LLM プロンプトにどう渡るか | ダミーのジョブで `{"wakeAgent": false}` と通常出力の両方を試す（ドキュメントでは注入方法が未確認） |
| 同梱プラグインのグループ応答を抑止できるか | 検証グループでは使わない。使う場合はソースで応答経路を確認 |

後藤さんには次の点を確認したい。第一に、Bot をグループに入れてよいか（メンバーに説明できるか、検証用の別グループを作れるか）。第二に、「人物A」とは誰か（グループに人物A がいるかの判定に使う、どの端末・アカウントの人か。Bot と友だちになってもらえるか）。第三に、対象となるグループはどれか、数はいくつか。第四に、LINE はスマホだけか、Mac 版・PC 版も使うか（段階 0 の手動エクスポートや、通知ミラー・画面読み取りの可否が変わる）。第五に、通知してほしい情報の具体像（日程調整、依頼事項、トラブル等）と、見逃し／誤通知のどちらを許容できるか。第六に、規約上グレーな手段を試す意思があるか、試す場合にサブアカウントを使えるか。

## 結論

最も大きな発見は、「Hermes で LINE を扱える」ことと「個人の LINE を読める」ことが別物だという点である。Hermes の LINE 対応は公式 Bot の窓口にすぎず、後藤さんの個人アカウントで見えている会話をそのまま読む道は、公式には開かれていない。したがって実現可否の分岐は技術ではなく、「Bot をグループに入れる合意が取れるか」で決まる。合意が取れるなら段階 1〜2 で規約上クリーンに実現でき、取れないなら、段階 0 の半手動運用が唯一のクリーンな選択肢となり、完全自動化はグレーな領域に踏み込む。

もう一つの含意は、検証の順序である。取得経路の議論に入る前に、段階 0 の手動データでローカル LLM の判断品質を測っておけば、取得手段への投資が見合うかを、リスクなしで先に判断できる。事例がほとんど見つからなかった領域（個人グループの自動要約、ローカル LLM との組み合わせ）だからこそ、最小の実験で得られる実機の知見が、このレポートの推論を補強する最も確かな材料になる。
