# iPhone 単体では自動検知できない、半自動なら今日できる

**結論から言うと、iPhone のショートカットとオンデバイス AI だけで、LINE Bot なしに「妻のいないグループの会話を自動で拾い、共有すべきものを検知して通知する」ことは、今回調べた範囲では成立しない。** LINE の本文を読むトリガーもアクションも iOS 26 には見つからず、iOS 27 beta で追加された「通知トリガー」も通知本文をショートカット側が読めない可能性が報告されている。できるのは、LINE の「トーク履歴を送信」を人が実行し、共有シートでショートカットに渡して以降（判定・整形・Telegram 送信）を自動化する「半自動」までである。この方式はグループ 1 つにつき約 5〜6 タップ（推論）で、Bot のようにメンバーへ見えることも、全発言をサーバーへ流すこともない。ただし「人が思い出して実行する」ことが前提なので、後藤さんが解決したい「努力に頼らない仕組み化」を完全には満たさない。判定には iPhone のオンデバイスモデル（約 3B、文脈 4K〜8K トークン）より、既に動いている Mac mini の Ollama のほうが現実的である。推奨（推論）は、今日は費用ゼロの運用（メンション依頼＋手動転送）で始め、半自動ショートカットを 30 分で実験し、取りこぼしが許容できない場合に限って Bot を足す段階案である。出典は [公式]（Apple・LINE の文書）、[3rd]（メディア・ブログ）、[逸話]（フォーラム・体験談）、[推論] に区別し、確認できなかった点は明記する。

## 自動取得の入口は iOS 26 には無く、iOS 27 beta でも不確実

ショートカットの個人用オートメーションには、確認なしで自動実行できるトリガーとして時刻、メッセージ、Wi-Fi、App、充電などが並ぶが、LINE のトーク本文を読めるものは含まれない ([Apple Shortcuts User Guide](https://support.apple.com/guide/shortcuts/apdfbdbd7123/ios)) [公式]。LINE 側にもトーク内容を読み取る App Intents／ショートカットアクションが公式に提供されている証拠は見つからず、紹介されているのは送信予約やトーク画面を開く程度である ([appllio](https://appllio.com/line-message-sending-reservation)、[linestep](https://linestep.jp/2023/02/21/line-shortcut/)) [3rd]。日本語の Apple コミュニティには、iOS 18 時点で LINE のアクションが表示されないという投稿もある ([Apple Community JP](https://discussionsjapan.apple.com/thread/255771191)) [逸話]。

唯一の望みは iOS 27 で追加された「アプリの通知」トリガーである。iOS 27 Developer Beta 1 では、通知を契機にショートカットを起動でき、ロック中でも実行されるが、本文フィルタが動かずフィルタなしでのみ発火した。検証は Home Assistant アプリだけで、他アプリへの適用は著者の推測にとどまる ([Derek Seaman](https://www.derekseaman.com/2026/06/home-assistant-notifications-that-run-apple-shortcuts-yes-really.html)) [3rd]。Homey のフォーラムには「発火するが通知の内容は読めない」という報告があり、返信は beta の制限で今後変わりうるとしている ([Homey Community](https://community.homey.app/t/ios-27-notifications-and-new-shortcuts/156044)) [逸話]。一方 MacStories は、自己通知である Deflector が通知本文をパースしていると述べており、可読性の報告は割れている ([MacStories](https://www.macstories.net/ios/deflector-turns-ios-27-notification-triggers-into-a-shortcut-launcher/)) [3rd]。つまり、LINE の通知本文が変数として取れるかは**未確認**である。仮に取れても、ミュート中のグループや通知プレビュー無効の場合は通知自体が来ないため、「今日の全発言」の代替にはならない [推論]。通知要約（Apple Intelligence）も表示専用で、自動化の入力になる API は確認できなかった ([Tom's Guide](https://www.tomsguide.com/ai/apple-intelligence/apple-intelligence-will-summarize-news-again-in-ios-26-after-false-headline-debacle)) [3rd]。

この表から読み取れる構造は明快で、「取得」の列だけが全手段で×か△であり、判定と通知は既に解決済みである。取得できないという結論は、Bot 方式を調べた先行調査とも一致する。LINE には履歴取得 API が無く、公式に手動エクスポートが残るだけという整理である [推論]。

「モデルを使用」アクションは iOS 26 で導入され、オンデバイス、Private Cloud Compute（PCC）、ChatGPT を選べ、出力は Boolean や Dictionary などの構造で受けられる ([MacStories iOS 26 review](https://www.macstories.net/stories/ios-and-ipados-26-the-macstories-review/8)) [3rd]。ただしオンデバイスモデルは約 3B パラメータ、文脈 4,096 トークンで、狭いタスク向けとされる（同記事）。iOS 26 beta の逸話では、未読 RSS 43 件でオンデバイスが文脈長で失敗し、ChatGPT は処理できた ([MacStories Q&A](https://www.macstories.net/notes/i-have-many-questions-about-apples-updated-foundation-models-and-the-great-use-model-action-in-shortcuts/)) [逸話]。iOS 27 では選択肢が On-Device、Cloud、Cloud Pro、Extension Model（ChatGPT）になり、対応機種は iPhone 15 Pro 以降、サーバー側モデルには 1 日の利用上限がある ([Apple Support](https://support.apple.com/guide/shortcuts/tpg3vrvwmclv)) [公式]。文脈長は、コードサンプルの 8192 と質疑で報じられた 4096（PCC は 32K）が食い違っており、確定できない ([WWDC26 session 241](https://developer.apple.com/videos/play/wwdc2026/241)) [公式・一部は検索スニペット]。同じ Apple のページは、自動化内で「モデルを使用」を動かす場合を扱っていない。日本語は iOS 27 の対応言語に含まれるが、判定精度の評価は見つからなかった。

Mac mini の Ollama を呼ぶ案は、Ollama の HTTP API を「URL の内容を取得」で叩く手順が日本語ブログで紹介されており ([Sansan Builders Box](https://buildersbox.corp-sansan.com/entry/2024/05/07/110000)) [3rd]、Tailscale にもショートカット用アクションがある ([Tailscale docs](https://tailscale.com/kb/1233/mac-ios-shortcuts/)) [公式]。一方で、iOS のショートカットから Tailscale の接続状態を確実に判定するのは難しいという報告があり ([Tailscale forum](https://forum.tailscale.com/t/shortcuts-support/3039)) [逸話]、iPhone→Tailscale→Ollama の実機報告は見つからなかった。

## 手間・信頼性・見え方で運用フローを比べる

実際に運用するなら、取得を「人が一手間かける」か「Bot に任せる」かの選択になる。先行調査と今回の調査を合わせ、現実的な 4 案を比べる。タップ数は LINE の画面構成からの推論で、実機では変わりうる。

| 観点 | ① iPhone 手動エクスポート型 | ② メンション運用 | ③ 共有リマインダー | ④ Bot 方式（Mac mini + Hermes） |
|---|---|---|---|---|
| 手間 | グループ 1 つにつき約 5〜6 タップ（グループ画面→メニュー→設定→トーク履歴を送信→共有先でショートカット選択）。5 グループなら約 25〜30 タップ／日 | 友人に「@後藤」を付けてもらう依頼のみ。後藤さん側の操作は通知を見るだけ | 気づいた人が 1 行追加。後藤さんのタップは 2〜3 回／件 | 初期構築のみ。日常はゼロ |
| 自動化度 | 低（起動は人。整形・判定・送信は自動） | 低（検知は友人の協力に依存） | 低（気づくのは人） | 高（受信から通知まで自動） |
| 費用 | 0 円（Telegram Bot は無料、Mac mini は既存） | 0 円 | 0 円 | 公式アカウントの無料枠内で足りる見込みだが、要確認 |
| 信頼性 | 中（実行を忘れた日は無効。ここが元の人的ミスと同じ構造） | 中（友人が付け忘れれば拾えない） | 中（気づかなければ入らない） | 高（ただし Bot 参加前・停止中の発言は取れない） |
| メンバーへの見え方 | 見えない | 友人にお願いが必要 | 見えない | Bot がメンバーとして見える（周知が望ましい） |
| プライバシー | 本文は端末→自宅 Mac かオンデバイス。外部クラウドを使わなければ家庭内で完結 | 本文は LINE 内のみ | 抜粋 1 行のみ | 全発言がサーバー（自宅 Mac）に到達する |
| 規約リスク | 低（公式のエクスポート機能と共有シートの範囲） | 低 | 低 | 低（公式 API 範囲。グループ参加の周知が前提） |

LINE 標準の「自分へのメンション通知」は、グループ通知をオフにしていても届き、全体設定でのみオフにできる ([マイナビニュース](https://news.mynavi.jp/article/20230705-2720447/)) [3rd]。したがって、友人が名指しで書いてくれる運用なら、通知を見逃しにくいのは事実である。一方、「LINE スマート通知」は公式アカウントからのニュース配信で、自分のトーク本文を監視する機能ではない ([All About](https://allabout.co.jp/gm/gc/492668/)) [3rd]。本文キーワードでの通知や自動転送機能は見つからなかったが、存在しないとは断定できない。

ここで正直に述べておくべき弱点がある。①は後半が自動化されても、「起動する」という最初の一手が人の努力に依存する。後藤さんが「努力での品質管理はできない」と判断した問題の本体は、まさにこの一手である。時刻オートメーションで「今夜 21 時にエクスポートを促す通知」を出すことはでき [推論]、これで思い出す負担は減るが、実行そのものは自動にならない。したがって、①は「取りこぼしゼロ」ではなく「漏れ確率を下げる」手段と位置づけるのが正確である。逆に④は、取りこぼしの本質（気づかない）を機械側に移せる唯一の案だが、他メンバーに Bot が見えるという社会的コストがある。

## 判定は Mac mini に置き、通知文は妻への転送文にする

推奨は段階的に進める。以下は調査結果からの**推論**であり、実機検証までは仮説として扱う。

最初の段階は、今日からできる費用ゼロの運用である。友人 1〜2 人に「妻に関係しそうな話題は @後藤 を付けて」と依頼し、通知をグループ単位でミュートしてもメンション通知だけが届く状態にする。気づいたときは LINE のメッセージ転送で妻とのトークに送るのが最短で、後藤さんの言う「手動なら転送が早い」と一致する。ここまでで LLM も Bot も要らない。

次の段階は、30 分で試せる半自動ショートカットで判定品質を検証することである。「トーク履歴を送信」の共有先に自分のショートカットが出るなら、受け取ったテキストを判定に回し、Telegram に送る構成を作る。判定の置き場所は 2 案ある。ひとつは、ショートカットから Mac mini の Ollama（Tailscale 経由）を直接呼ぶ案で、モデルを大きくでき、日本語精度と文脈長の不安を避けられる。もうひとつは、ショートカットがエクスポートした本文を既存の Telegram ゲートウェイ経由で Hermes に渡し、Hermes 側で判定させる案で、Tailscale の到達性を気にせずに済む可能性がある [推論・未検証]。オンデバイスの「モデルを使用」は、プライバシーが最良で追加費用もないが、文脈が 4K〜8K トークンで長い日のグループ会話は分割が必要になり、日本語の判定精度も未確認のため、「本文が短い場合の第 1 候補」という位置づけにとどめる。

通知文面は、後藤さんが Telegram で見てそのまま妻に転送できる形に整える。たとえば「【妻に共有？】友人の結婚式の日程が話題。要点：日時・場所。元の発言：（該当 1〜3 行）。」のように、判定理由と原文の抜粋を同じメッセージに入れる。妻に直接送る文として書けば、後藤さんの作業は転送ワンタップに減る [推論]。判定結果に確信度が低い場合は「念のため」と明記し、見逃しより過検知を許容する設計にする。

最後の段階として、①の運用でも漏れが続く、あるいはグループ数が多く毎日の手動が現実的でないと分かった場合にだけ、Bot 方式へ進む。Hermes と Mac mini は、受信・蓄積・判定・Telegram 通知の部分で既に準備済みであり、追加で必要なのは LINE 側の Bot 登録と、メンバーへの周知である。

## 未確認事項と、iPhone 上で 10〜30 分でできる検証

今回の調査は検索ベースで、実機検証はしていない。以下は結論を左右する未確認事項である。

| 未確認事項 | 確かめ方（10〜30 分） |
|---|---|
| 「トーク履歴を送信」の共有先にショートカットが出るか、テキストかファイルか | 小さなショートカット（共有シートから受け取って「テキストを表示」）を作り、ダミーのグループで履歴を送信してみる |
| エクスポートの形式（日付見出し、今日だけの絞り込み可否、サイズ） | 上記の出力をそのまま見て、日付行を確認する。長いトークでの上限も試す |
| 「モデルを使用」（オンデバイス）の日本語判定精度と文脈長 | 結婚式の話題を含む実際に近いテキストを数件貼り、Boolean で判定させる。長さを増やして失敗点を探す |
| 画面ロック中や自動化経由で「モデルを使用」が動くか | 時刻オートメーション（実行前の確認なし）に組み込み、画面をロックして 5 分後に結果を見る |
| Ollama を Tailscale 経由で呼べるか、外出先（モバイル回線）でも動くか | 「URL の内容を取得」で Ollama の API に短い POST を送る。Wi-Fi オフでも試す |
| Telegram Bot API への POST（長文は 4096 字制限で分割要） | 短文・長文の両方で試す |
| iOS 27 の通知トリガーで LINE 通知の本文が取れるか | 通知トリガーを LINE に設定し、変数の中身を「テキストを表示」で確認する。ミュート中のグループでも試す |

後藤さんに確認したい質問は 6 つある。第一に、iPhone の機種と iOS バージョン（15 Pro 以降で iOS 26／27 のどちらか）。第二に、妻のいないグループの数と、1 日の発言量の目安。第三に、現在の LINE の通知設定（グループごとのミュート、通知プレビューの有無、メンション通知の設定）。第四に、友人にメンションを依頼することへの抵抗感（Bot の参加より受け入れやすいか）。第五に、「見逃しの許容度」（週に何回までなら許せるか）。第六に、妻への転送を LINE で行うか、Telegram 経由のままにしたいか。

## Conclusion

今回の調査で明らかになったのは、問題の分解図が思ったよりも偏っていたことである。判定、整形、通知は、iPhone でも Mac mini でも既に解ける。解けないのは「取得を人の努力に頼らない」ことの一点で、iPhone 単体の手段はその一点で全て行き詰まる。つまり、後藤さんの選択は「Bot か iPhone か」ではなく、「取得の一手を人が担う限り、仕組みは努力の関数のままである」という認識に帰着する。

実務上の含意は、費用ゼロの層（メンション依頼＋転送）で効果を見てから、半自動の検証で追加の価値を測り、取りこぼしが実害に見合う場合に限って Bot を入れるという順序である。iOS 27 の通知トリガーが正式版で本文を読めるようになれば状況は変わりうるが、取りこぼしの性質は残る。現時点では、これは推論であり、先の 7 つの小さな実験が最初の根拠を与える。
